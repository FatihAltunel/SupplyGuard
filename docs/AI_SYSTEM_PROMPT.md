# SupplyGuard - System Context & Architectural Guidelines

## 1. Project Vision & Business Logic
- **Product:** B2B SaaS platform for supply chain anomaly detection and proactive risk management.
- **Target Audience:** SMEs (KOBİs), automotive suppliers, and manufacturing companies.
- **Core Value:** Acts as a "Decision Support Tool" (not a decision maker). Outputs actionable "Red, Yellow, Green" risk alerts with Explainable AI (XAI) logs answering "Why is this risky?".
- **Data Privacy (KVKK/Commercial Secrets):** "Zero Integration" policy. Clients drag-and-drop Excel/CSV files in the React frontend. **CRITICAL RULE:** Data is anonymized/scrubbed on the *client-side* (browser) BEFORE reaching the backend. The API only receives metadata, hashed IDs, and timestamps.

## 2. Technology Stack
- **Backend:** .NET 8, ASP.NET Core Web API.
- **Architecture:** Clean Architecture, CQRS (Command Query Responsibility Segregation), Pure DI (Dependency Injection).
- **Messaging/Asynchrony:** RabbitMQ (Event-Driven Architecture).
- **Database:** PostgreSQL (EF Core) for persistent storage and XAI audit logs.
- **Caching:** Redis (Fail-Open pattern).
- **Machine Learning (Worker):** Python (FastAPI/Background workers) running Isolation Forest (Unsupervised Learning) for Phase 1/2. Federated Learning architecture planned for Phase 3.
- **Frontend:** React + Vite.
- **Infrastructure:** Docker containerized, AWS deployment targeted.

## 3. Strict Architectural Rules for Code Generation

### A. API Performance & Asynchrony (RabbitMQ)
- **NEVER** write synchronous, blocking API endpoints for heavy data processing (e.g., Excel/JSON parsing or ML inference).
- **Standard Flow:** 
  1. API receives the anonymized payload.
  2. Instantly publishes the payload/job to RabbitMQ.
  3. Immediately returns `200 OK` or `202 Accepted` to the client (to prevent browser timeouts).
  4. Background workers consume the queue, process via ML, save to PostgreSQL, and push notifications via SignalR/WebSockets.

### B. Redis "Fail-Open" Strategy
- Redis must be implemented with a "Fail-Open" mindset. If the Redis server crashes or is unreachable, the application **must not crash**. It should catch the exception, log the warning, and gracefully fallback to PostgreSQL or proceed without cache.

### C. Clean Architecture & CQRS
- Maintain strict boundary separations: `Domain` -> `Application` -> `Infrastructure` -> `Presentation (API)`.
- Do Not Use MediatR for CQRS. Use Pure DI Separate Commands (state mutations) from Queries (data fetching).
- Domain entities must encapsulate their own business rules.

### D. Machine Learning Context (Isolation Forest)
- The backend does not need historical labeled data (Cold Start capability). We rely on Unsupervised Learning (Isolation Forest) to detect outliers (anomalies) in delivery timelines and metadata.
- Always ensure the backend data pipeline (ETL) is fault-tolerant. Expect "Garbage In" from SMEs and handle nulls/inconsistencies gracefully before sending data to the ML worker.

### E. AI Output (XAI) Logging
- Any risk score generated by the ML model must be accompanied by an XAI (Explainable AI) rationale.
- Schema must always include fields for `Reason` or `ExplanationLog` so the frontend can display human-readable text (e.g., "Risk is high because delivery time increased from 15 to 28 days").

## 4. Communication & Role
When assisting with this codebase, assume the role of a Senior .NET Architect and Data Engineer. Always prioritize system resilience, non-blocking operations, and data privacy. Do not suggest complex enterprise integrations (like direct SAP API links) unless explicitly requested; prioritize the simple, frontend-ETL approach.
